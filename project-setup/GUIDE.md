# GUIDE.md - 项目接入指南

目标：**30 分钟内让 AI 能在这个项目里安全地干活。** 产出物是一份项目自己的 `AGENTS.md`，
不需要任何额外配置文件。

---

## 一、先弄清五件事

接入的核心不是抄文档，而是把这五个事实查清楚并写下来。查不清就写"未知"，
不要编。

| 要弄清 | 去哪里找 | 写进 AGENTS.md 的位置 |
|---|---|---|
| 怎么构建、怎么跑 | `README`、`package.json` / `Makefile` / `pom.xml`、CI 配置 | 常用命令 |
| 快测和门禁分别是什么命令 | CI 配置、贡献指南、问维护者 | 快测 / 门禁 |
| 哪些目录是高危 | 认证、支付、迁移、发布配置、基础设施 | 高风险目录 |
| 哪些目录不能动 | 生成的代码、vendor、构建产物、二进制资源 | 禁改目录 |
| 文档放哪、谁是权威 | 现有 `docs/`、wiki、设计文档 | 文档约定 |

判断命令是否可信的标准：**你自己跑过，且退出码为 0。** 只看 README 写的不算。

---

## 二、新项目

1. 建立版本控制与基础测试（没有这两样，本规范的大部分规则无法执行）。
2. 复制 [templates/AGENTS.md](../templates/AGENTS.md) 到项目根目录，改名 `AGENTS.md`。
3. 填四个部分：
   - 常用命令（装依赖、跑、快测、门禁）
   - 目录结构与职责边界
   - 高风险目录、禁改目录
   - 文档约定（哪些文档存在、谁维护）
4. 让 AI 跑一次项目状态（可选，项目还小可以先跳过）：

   ```text
   按 <规范库>/prompts/PROJECT-SCAN.md 扫描当前项目，生成 docs/PROJECT-STATE.md。
   ```

5. 按需复制 [templates/docs/HANDOVER.md](../templates/docs/HANDOVER.md)，
   只在需要跨会话交接时维护。
6. 用一次真实的小改动试跑：按 [coding/WORKFLOW.md](../coding/WORKFLOW.md) 定级、改、验证。

不需要做的事：

- 不需要一次建齐 `docs/` 下所有文件。用到再建。
- 不需要为每个功能建功能卡。
- 不需要引入本库的任何"配置协议"。

---

## 三、老项目

原则：**先只读盘点，再写约定，最后小步试点。** 不要一边盘点一边改代码。

### 步骤 1：让 AI 自己摸清项目（不手写盘点）

不用人工填表。两种方式，可叠加：

```bash
# 客观事实（只读，跨平台，纯标准库）
python <规范库>/scripts/scan_project.py --root . --out docs/PROJECT-FACTS.md
```

```text
# 语义判断：把下面这句话发给 AI
按 <规范库>/prompts/PROJECT-SCAN.md 扫描当前项目，生成 docs/PROJECT-STATE.md。
只读，不要改代码，不要装依赖。
```

扫描会产出：技术栈、命令（出处 + 是否验证）、目录地图、高危与禁改**候选**、
git 现状、TODO 分布、文档与代码的冲突、待确认项。

**扫描不改代码、不装依赖、不跑测试。** 命令默认标"未验证"，需要你允许后才实际跑。

### 步骤 2：人工只确认三件事

扫描结果里只有三样必须人来定：

1. **高危目录**是不是真的是高危（AI 只能按命名给候选）
2. **禁改目录**是否完整（生成物、第三方、密钥）
3. **命令**是否真的能跑（跑一次，看退出码）

其余内容（技术栈、目录、进度、坑）让 AI 自己维护，不需要你逐条校对。

### 步骤 3：生成极简 `AGENTS.md`

让 AI 按 `docs/PROJECT-STATE.md` 填一份 `AGENTS.md`（用模板），你只复核：

- 命令是不是你跑通的那几条
- 高危 / 禁改是不是刚确认过的
- 有没有多写了废话（超过 8 KB 就删）

写完之后，`AGENTS.md` 只管**路由和边界**；项目细节一律看状态文档，
状态文档过时了就说"更新项目状态"，不要手工修补。

### 步骤 4：处理文档冲突

老项目常见"文档写的和代码做的不一样"。处理规则：

1. **以代码和 CI 的实际行为为准。**
2. 冲突不自行裁决，列成清单交给项目负责人决定。
3. 决定后只保留一份说法：更新文档，或在 `AGENTS.md` 里明确写"忽略某文档的某条"。

### 步骤 5：试点

挑一个**绿灯**任务（小 bug、文案、局部修正），完整走一遍：定级 → 改 → 快测 → 汇报。
试点不顺利就先修 `AGENTS.md` 里的命令和目录，不要急着接大任务。

试点通过后，再逐步放开黄灯任务。

## 四、`AGENTS.md` 里必须有的内容

```text
1. 这个项目是什么（一句话）
2. 常用命令：装依赖 / 本地跑 / 快测 / 门禁
3. 目录地图：哪里放什么，哪些是核心
4. 高风险目录：默认按最高等级处理
5. 禁改目录：生成物、第三方、构建产物
6. 文档约定：权威文档在哪、哪些已废弃
7. 项目特有的偏离：覆盖了哪条通用原则，范围多大
```

不必须有的：团队花名册、进度表、历史沿革、完整规范抄本。

---

## 五、多仓库 / 多服务项目

- 每个仓库一份自己的 `AGENTS.md`，写本仓库的命令与边界。
- 跨仓库的约定放在一个独立的约定仓库或文档，各仓库链接过去，不复制。
- 跨仓库改动默认按红灯处理：列出所有受影响仓库、发布顺序、回滚方式。

---

## 六、常见坑

- 把 README 里的命令直接抄进 `AGENTS.md`，没跑过 → AI 按错的命令验证，一路绿灯假象。
- 一次接入就写几千字规范 → 没人读，AI 也只读到前面几段。先短，再按需扩。
- 只写"不要做什么"，不写"怎么做" → AI 卡住或自由发挥。
- 高风险目录漏了迁移脚本和发布配置 → 最容易出事故的地方恰好没保护。
- 老项目文档冲突不处理，直接两套并存 → 后续所有判断都在摇摆。

---

## 七、验收清单

- [ ] 快测命令与门禁命令我都亲自跑通了
- [ ] 高风险目录、禁改目录已写并和负责人确认过
- [ ] `AGENTS.md` 小于 8 KB，只有路由和事实，没有大段原则抄写
- [ ] 老项目已生成 `docs/PROJECT-STATE.md`，"待确认"项已处理
- [ ] 文档冲突已列出并得到裁决
- [ ] 完成一次绿灯试点，流程跑通
- [ ] 团队知道：合并主干、发布、改数据结构都需要单独确认
