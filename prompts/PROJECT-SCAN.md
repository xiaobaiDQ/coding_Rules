# PROJECT-SCAN.md - 项目扫描提示词

让 AI 用**一次只读扫描**，把"这个项目是什么、做到哪了、有哪些坑"写成一份可复查的文档。
适用于：新接手的项目、开发到一半的项目、隔很久回来的项目。

产物：`docs/PROJECT-STATE.md`（项目状态），可反复重跑刷新。

---

## 怎么用

**首次扫描**（把 `<规范库>` 换成本仓库的实际路径）：

> 按 `<规范库>/prompts/PROJECT-SCAN.md` 扫描当前项目，生成 `docs/PROJECT-STATE.md`。
> 只读，不要改代码，不要装依赖。

**日常更新**（增量，不重写全文）：

> 更新项目状态。

**刷新路由**：扫描后如果发现命令或目录变了，问用户是否同步更新 `AGENTS.md`。
`AGENTS.md` 里人工写的内容，任何时候都不要自动覆盖。

---

## 硬约束

1. **只读。** 可以读文件、列目录、跑只读命令（`git status` / `git log` / `git diff`、版本查询）。
2. **不执行改变状态的操作**：不装依赖、不跑构建、不跑测试、不迁移、不提交、不推送、不改配置。
   必须跑才能确认的结论，标"未验证"，并在"待确认"里写清要跑什么命令。
3. **只写一个文件**：`docs/PROJECT-STATE.md`。用户明确同意后才动 `AGENTS.md`。
4. **不臆造。** 每条事实带证据；没有证据写"推测"；查不到写"未找到"。
5. **不为了填满表格编内容。** 表格空着比写假话好。

---

## 证据标注

| 来源 | 写法 |
|---|---|
| 读文件 | `证据: package.json` |
| 跑命令 | `已验证: git log -5`（附关键输出一行） |
| 推断 | `推测: 目录结构像是 monorepo` |
| 互相矛盾 | `冲突: README 写 yarn，但仓库有 pnpm-lock.yaml` |

## 扫描步骤

控制总量：优先读清单文件和目录结构，不要通读整个仓库，不要把大文件贴进上下文。

### 1. 先看清单，确定技术栈
`package.json` / `pyproject.toml` / `go.mod` / `Cargo.toml` / `pom.xml` / `build.gradle` /
`composer.json` / `Gemfile` / `*.csproj` / `Makefile` / `Dockerfile` / `docker-compose.yml`。
有锁文件就记下来（决定用哪个包管理器）。

### 2. 目录结构与规模
顶层目录、各自职责、文件数量级。找出：源码、测试、文档、生成物、第三方目录。
如果项目有 `scripts/scan_project.py` 可用（规范库提供），可先跑它拿客观事实，再补语义判断。

### 3. 命令从哪里来
优先看：`<manifest>.scripts`、`Makefile`、`justfile`、CI 配置（`.github/workflows/`、
`.gitlab-ci.yml`、`Jenkinsfile`）、`README`、`CONTRIBUTING`。
记录每条命令的**出处**。README 里的命令如果没有实际跑过，标"未验证"，不要当成事实。

### 4. 测试与质量门禁
测试目录、测试框架、覆盖率配置、lint/format/typecheck 配置。
注意"假门禁"：CI 里被 `continue-on-error`、`|| true`、`skip` 跳过的检查。

### 5. 版本控制现状
`git status --short`（有多少未提交改动）、`git log --oneline -10`（最近在干什么）、
当前分支、和主分支的差距、有没有长期未合并的分支。
（只读命令；不要 fetch、不要 merge。）

### 6. 未完成的迹象
`TODO` / `FIXME` / `HACK` 的分布、被 `.skip` / `xit` / `@Ignore` 的测试、
被注释掉的大段代码、`deprecated` 标记、临时开关。
只统计数量和位置，不要贴大段内容。

### 7. 高危与禁改候选
按目录名和内容判断候选（认证、支付、迁移、发布、基础设施、密钥）。
**只能给候选，必须标"待人工确认"**，不能自行定为规则。

生成物目录（`dist` / `build` / `target` / `vendor` / `generated` / `node_modules`）
列为禁改候选。

### 8. 文档与代码是否一致
文档声称的命令/架构，和仓库实际是否一致。冲突逐条列出，不自行裁决。

### 9. 未知项
你没能确认的东西，全部列进"待确认"，写清楚需要什么信息才能确认。
这一节不许留空话，宁可写"没有找到部署配置，部署方式未知"。

## 输出格式

严格按 `templates/docs/PROJECT-STATE.md` 的章节顺序写。要求：

- 顶部写：生成时间、扫描范围（哪些目录没看）、未验证项数量。
- 每节内容控制在能快速读完的长度；目录地图用树状，不列全部文件。
- 高危/禁改候选单独一个表，带"确认状态"列（默认"待确认"）。
- "下一步建议"最多 3 条，每条写清为什么是现在做。

**增量更新时：**

- 保留 `<!-- 人工确认区 begin -->` 到 `<!-- 人工确认区 end -->` 之间的内容，一字不改。
- 只改有变化的章节，并在该章节末尾加 `<!-- 更新: YYYY-MM-DD 原因 -->`。
- 顶部更新时间要刷新；没变化的章节不要重写。

---

## 完成后汇报（3 句话，不要长篇）

1. 这是个什么项目，什么技术栈。
2. 现在最该注意的问题是什么（卡点/风险/坑）。
3. 建议下一步做什么，需要用户确认什么。

然后告诉用户：状态已写入 `docs/PROJECT-STATE.md`，哪些项标了"待确认"。

---

## 禁止

- 把"推测"写成"已确认"
- 用 README 里的命令冒充"已验证"
- 为了让文档看起来完整，编造构建/部署/测试方式
- 扫描时顺手改代码、装依赖、提交
- 自动修改 `AGENTS.md` 或覆盖人工确认区
- 一次贴出整个仓库的文件内容
