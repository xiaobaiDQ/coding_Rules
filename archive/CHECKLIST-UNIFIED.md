## 核心原则检查清单

**使用场景：** 任何改动前

### 四大原则检查清单（通用）

在开始任何改动时，使用这个清单：

| 原则 | 检查项 | 具体说明 |
|------|--------|--------|
| **Think Before Coding** | 我明确了所有假设吗？ | 不确定就问，不要瞎改 |
| | 我问了所有不确定的地方吗？ | 列出多种理解和权衡 |
| | 我列出了多种做法的权衡吗？ | 至少给出 2 个方案 |
| | 涉及技术方案时，我在GitHub查找了参考吗？ | 见 GITHUB-RESEARCH.md |
| **Simplicity First** | 这段代码做的事情超出需求吗？ | 删除多余功能 |
| | 有多余的抽象吗？ | 单次使用的就内联 |
| | 能用50行代替200行吗？ | 能就改成50行 |
| | 我为低概率事件添加防御了吗？ | 必须先问用户，经确认再加 |
| | 我有层层重复的校验代码吗？ | 见规则2.2：入口单次校验 |
| | 我为单次使用的逻辑拆分了函数吗？ | 见规则2.3：三次复用再抽象 |
| | 我用try-catch了吗？能简化吗？ | 见规则2.4：用结果类型替代 |
| **Surgical Changes** | 我是否改动了相邻的无关代码？ | 只改需求部分 |
| | 我是否匹配了现有的代码风格？ | 保持风格一致 |
| | 每改一行都能追溯到需求吗？ | 100% 追溯率 |
| **Goal-Driven Execution** | 我明确定义了成功标准吗？ | 写出可验证的目标 |
| | 我有验证计划吗？ | 列出检查点 |
| | 完成后我验证了吗？ | 循环直到验证通过 |

## 改动类型判断清单

**使用场景：** 接到改动需求时

### 是否是简单改动？

同时满足以下所有条件才是简单改动：

```
[ ] 代码改动 < 50 行
[ ] 单文件改动（或最多 2-3 个紧密相关文件）
[ ] 不改 API 签名
[ ] 不改数据结构
[ ] 不改公开接口
[ ] 原因明确，不需要方案设计
[ ] 没有系统级影响
[ ] 没有API变化

✅ 所有项都打勾 → 简单改动
❌ 有任何一项不打勾 → 升级到常规改动
```

### 是否是常规改动？

以下任何一个成立就是常规改动：

```
[ ] 代码改动 50-500 行
[ ] 新增功能模块
[ ] 修改现有模块的关键逻辑
[ ] 外部依赖（新库、新服务调用）
[ ] 性能优化
[ ] 安全相关改动
[ ] 数据库迁移或表结构变更
[ ] 需要制定方案，但方案明确
[ ] 有系统级设计，但不复杂

✅ 有任何一项打勾 → 常规改动
❌ 都没有打勾且不超 500 行 → 简单改动
```

### 是否是复杂改造？

以下任何一个成立就是复杂改造：

```
[ ] 代码改动 > 500 行
[ ] 跨多个子系统的改动
[ ] 架构级改变（重构组织结构）
[ ] 高风险改动（认证、支付、数据处理等）
[ ] 需要多个依赖项更新
[ ] 重大的不确定性（可能需要多轮迭代）
[ ] 需要多个 Agent 分阶段执行
[ ] 需要多个团队配合

✅ 有任何一项打勾 → 复杂改造
❌ 都没有打勾 → 常规改动
```

## 项目适配检查清单

**使用场景：** 项目初始化时

### 扫描项目现状

```
[ ] 读了项目的 package.json / build config 吗？
[ ] 读了 README.md / CONTRIBUTING.md 吗？
[ ] 查找了现有的 linter/formatter 配置吗？
[ ] 评估了项目成熟度吗？
[ ] 记录了所有发现吗？
```

### 对比规范

```
[ ] 逐项对比通用原则（Think/Simplicity/Surgical/Goal-Driven）
[ ] 逐项对比改动流程（简单/常规/复杂定义）
[ ] 逐项对比验收标准
[ ] 标记了每个冲突的影响等级
```

### 生成冲突报告

```
[ ] 冲突总览完整（总数、高/中/低影响各几个）
[ ] 每个冲突的详情清晰（冲突是什么、影响是什么）
[ ] 决策选项写得够清楚（3-4个选择）
[ ] 影响分析准确
```

### 用户决策

```
[ ] 展示了冲突报告
[ ] 给出了建议方案
[ ] 等待用户逐个决策
```

### 应用决策

```
[ ] 正确理解了用户的所有决策
[ ] 生成了 PROJECT-ADAPT.yaml
[ ] 记录了理由和时间戳
```

## 项目适配检查清单

**使用场景：** 项目初始化时

### 扫描项目现状

```
[ ] 读了项目的 package.json / build config 吗？
[ ] 读了 README.md / CONTRIBUTING.md 吗？
[ ] 查找了现有的 linter/formatter 配置吗？
[ ] 评估了项目成熟度吗？
[ ] 记录了所有发现吗？
```

### 对比规范

```
[ ] 逐项对比通用原则（Think/Simplicity/Surgical/Goal-Driven）
[ ] 逐项对比工作流（简单改动/常规改动/复杂改造定义）
[ ] 逐项对比验收标准
[ ] 标记了每个冲突的影响等级
```

### 生成冲突报告

```
[ ] 冲突总览完整（总数、高/中/低影响各几个）
[ ] 每个冲突的详情清晰（冲突是什么、影响是什么）
[ ] 决策选项写得够清楚（3-4个选择）
[ ] 影响分析准确
```

### 用户决策

```
[ ] 展示了冲突报告
[ ] 给出了建议方案
[ ] 等待用户逐个决策
```

### 应用决策

```
[ ] 正确理解了用户的所有决策
[ ] 生成了 PROJECT-ADAPT.yaml
[ ] 记录了理由和时间戳
```

## 文档维护检查清单

**使用场景：** 修改规范库时

### 修改前

```
[ ] 我明确了要改什么吗？
   [ ] 是简单改动/常规改动/复杂改造定义吗？
   [ ] 是编码原则吗？
   [ ] 是Skill吗？
   [ ] 是检查清单吗？
[ ] 我查了 DOC-MAINTENANCE-GUIDE.md 对应的情况吗？
[ ] 我知道需要同步哪些文件了吗？
```

### 修改时

```
[ ] 在所有需要的文件中都进行了修改吗？
[ ] 保持了说法一致吗？
[ ] 相同概念用了相同的词吗？
```

### 修改后

```
[ ] 我验证了一致性吗？
   [ ] 搜索关键词，确保所有地方都改了
   [ ] 检查新旧版本有无矛盾
[ ] 我更新了 docs/DECISIONS.md 吗？
   [ ] 记录了规范改动
   [ ] 说明了原因和影响范围
[ ] 我通知了所有相关项目吗？（如果有改动影响）
```
