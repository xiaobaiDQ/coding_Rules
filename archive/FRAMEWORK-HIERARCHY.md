# FRAMEWORK-HIERARCHY.md - 规范体系分级结构

**对象：** 任何想快速理解 vibcoding 规范体系的人

**目的：** 清晰的分级，消除混乱感

---

## 🏗️ 四层分级体系

```
【L0】最小化启动（必读，5分钟）
      ↓
【L1】核心规范（必读，30分钟）
      ↓
【L2】应用框架（推荐读，1小时）
      ↓
【L3】扩展和深化（选读，自主决定）
      ↓
【L4】项目专有（项目创建时）
```

## 推荐阅读路径

### 路径 1：我是新人（新 AI 或新开发者）

```
1. 读 QUICK-START-5MIN.md                    (5分钟)
2. 读项目的 AGENTS.md                        (3分钟)
3. 读项目的 PROJECT-ADAPT.yaml               (2分钟)
4. 准备好了，开始工作
5. 有问题时查 CHECKLIST-UNIFIED.md 或详细文档
```

### 路径 2：我要执行一个改动

```
1. 判断改动类型 → 查 CHECKLIST-UNIFIED.md 中的判断清单
2. 加载项目规范 → 读项目的 PROJECT-ADAPT.yaml
3. 执行对应工作流 → 参考 WORKFLOW.md 或 AI-EXECUTION-GUIDE.md
4. 完成后更新文档 → docs/progress.md + docs/decisions.md
```

### 路径 3：我要适配一个新项目

```
1. 读 PROJECT-ADAPT-STRATEGY.md              (理解流程)
2. 执行项目扫描 → 查 CHECKLIST-UNIFIED.md 中的项目适配清单
3. 生成冲突报告 → 展示给用户
4. 创建 PROJECT-ADAPT.yaml → 机器可读的配置
5. 创建项目的 AGENTS.md → 人类可读的说明
```

### 路径 4：我要修改规范库本身

```
1. 读 DOC-MAINTENANCE-GUIDE.md               (了解同步点)
2. 在所有需要的地方进行修改
3. 验证一致性
4. 更新 docs/DECISIONS.md
```

## 【L1】核心规范 ⭐⭐⭐⭐⭐（必读，30分钟）

**适合谁：** 所有在这个规范体系下工作的 AI 和人类

**核心问题：** "怎样写好代码？怎样做好工作流？"

### 子层 1.1：编码原则（15分钟）

| 文档 | 内容 | 必要性 |
|------|------|--------|
| **PRINCIPLES.md** | Karpathy四原则 + 4条深化规则 | 必读 ✅ |

**关键价值：**
```
这是整个规范的"哲学基础"
不管用什么技术、做什么项目、什么工作流
这四个原则都适用

Think Before Coding → 避免瞎改
Simplicity First → 代码保持简洁
Surgical Changes → 只改必需部分
Goal-Driven Execution → 明确目标验证结果
```

### 子层 1.2：工作流（15分钟）

| 文档 | 内容 | 必要性 |
|------|------|--------|
| **WORKFLOW.md** | L1/L2/L3 三级工作流 + AI自主性范围 | 必读 ✅ |

**关键价值：**
```
这是整个规范的"执行框架"

判断什么时候用L1/L2/L3
知道在每个级别AI能做什么、不能做什么
明确AI和用户的边界

L1：完全自主
L2：自主执行，方案确认后自主到底
L3：深度设计，关键决策等确认
```

**这一层输出：**
```
✅ 理解四大编码原则
✅ 能正确判断工作流级别
✅ 知道AI的自主性范围
✅ 能按照规范执行工作
```

## 【L3】扩展和深化 ⭐⭐⭐（选读，自主决定）

**适合谁：** 想要扩展规范的人、高级用户、有特殊需求的项目

**核心问题：** "我可以怎样在这个框架基础上扩展？我的项目有特殊需求怎么办？"

### 子层 3.1：规范扩展

| 文档 | 内容 | 适用场景 |
|------|------|---------|
| **skills/OIL-DEV-SKILLS-EXTENSION.md** | 在通用Skill基础上扩展 | 想加"SQL审查"、"性能检查"等 |
| **skills/PROJECT-CUSTOM-SKILLS-STRATEGY.md** | 创建项目级Skill的完整指南 | 项目有非常特殊的需求 |

**关键价值：**
```
这一层处理"不够通用"的问题

不够通用 = 大部分项目用这个规范 + 某个项目需要特殊处理

扩展方式：
1. 能用通用规范吗？→ 用
2. 不够完善？→ 在基础上扩展（supplement）
3. 完全不同？→ 创建项目Skill（replace）
```

### 子层 3.2：信息提取（老项目迁移）

| 文档 | 内容 | 适用场景 |
|------|------|---------|
| **project-adapt/DOCS-EXTRACTION-GUIDE.md** | 从现有项目文档提取信息 | 老项目迁移到新规范 |

**关键价值：**
```
老项目已有很多文档和规范
新规范怎样避免冲突？
怎样平滑过渡？

这个文档告诉你整个迁移流程
```

**这一层输出：**
```
✅ 知道怎样扩展通用规范
✅ 知道怎样创建项目Skill
✅ 知道怎样迁移老项目
✅ 能处理特殊和复杂的场景
```

```

├─ docs/
│  ├─ HANDOVER.md            ← 交接文档

│  └─ PROGRESS.md            ← 项目进度记录
│
└─ skills/（如果有项目Skill）

   ├─ skill-perf-check/SKILL.md
   └─ ...
```

**这一层特点：**
```
✅ 完全项目专有
✅ 不可能通用
✅ 每个项目都不同
✅ 在 PROJECT-ADAPT-STRATEGY.md 中创建
```
